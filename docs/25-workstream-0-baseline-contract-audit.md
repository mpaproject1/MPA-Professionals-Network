## 1. Audit method and limits

This audit inspected the merged `main` source, route/component files, membership/payment migrations, relevant service modules, and existing automated test names/content. It did **not** change application code, add a database migration, run CI, access the development deployment, or execute browser interactions. CI is intentionally deferred until the final workstream, per instruction.

The reported behaviors are treated as **user-observed in the development environment**. Repository evidence below confirms several route/component/contract gaps, but the exact development browser reproduction, live API response payloads, server logs, and member-card error reference `df974b25dc9c09f48405c6906897583d` have not been independently reproduced or traced from this environment. Do not describe those items as independently reproduced until the development environment is exercised.

Classification:
- **Confirmed in code:** the current source directly demonstrates the mismatch or missing UI.
- **Likely contract/integration gap:** UI expects a field/capability but the inspected UI contract does not provide it; verify the actual API payload and handler before deciding whether backend code is missing.
- **Needs environment reproduction:** requires an authenticated browser/API response, test account, server log, or data row unavailable in this repository-only audit.

## 2. High-level findings

1. The current main navigation defines `/member` (singular, label “My workspace”), not `/members`. No `web/app/members` route exists in the inspected App Router directory. The current personal workspace route and the user's reported `/members` URL must be reconciled before redesign.
2. `/membership` and `/membership/payment` exist. The membership workspace already has application progress/status UI and a private file upload flow for **application attachments**. However, its payment-submission function sends amount, channel, reference and idempotency key without attaching a receipt to the payment transaction. This conflicts with the documented manual-payment evidence contract.
3. A payment-method database migration exists (`20261028100000_membership_payment_methods.sql`) with bank/account fields, but the inspected admin route inventory shows no dedicated payment-method configuration page. Existing `/admin/membership` reuses the membership workspace; `/admin/membership-card` configures card branding, not bank payment instructions. This is a strong UI/API discoverability gap; route/service completeness still needs endpoint tracing.
4. The guide launcher fetches server-defined guides for the current route and spotlights each step's CSS selector. Current shell markup uses generated IDs such as `<shellId>-brand` and `<shellId>-sync`, while older guide data in migrations targets fixed IDs such as `#mpa-brand` and `#mpa-sync`. This makes at least the global navigation tour stale against the current shell markup.
5. `/admin/members/catalog` links to `/admin#account-governance`; the user reports this falls back to Admin Overview. The link is present in source. Whether a matching section is rendered is to be checked in the admin overview; the current UX should use a real section route/anchor and direct-navigation test.
6. Account management already offers account status changes, a sign-in recovery-link request, and session revocation. The current `UsersTable` has no visible issue/download one-time-password action or recovery-email edit action. It also renders missing membership/organization data as “Not available from this account response,” and profile detail depends on optional `profile` data returned by the API.
7. The member catalogue response/UI contains only a narrow set of attributes (name, email, phone, membership number, product, status, validity and account link/status). Its dedicated import/export page offers CSV/XLSX export filtered by query/status, but no field/column selection. The non-member account catalogue is a separate `/admin/accounts` screen, limited to up to 200 accounts per load and not a unified selective-export workflow.
8. Member card rendering exists for one membership number, but the member route intentionally shows “Membership card unavailable” when the card API fails or no eligible record is returned. Admin branding can open one card by membership number. No bulk card print action is visible in the inspected UI. The specific reported error reference requires server-side trace and data lookup; do not assume it is a UI-only defect.
9. The job-interest UI explicitly displays the private continuation token and asks the user to retain it. It also calls endpoints named `/api/v1/public/opportunity-inquiries/...`. This is incompatible with the desired user experience and raises a scope question. The token must remain a secret server-side credential; a human-readable request reference must not become an access credential. The server's authorization policy must be confirmed at every route before classifying members-only enforcement as missing.
10. No schema migration is justified by this audit alone. Existing payment-method, private-upload, membership, account-security, tracking-reference, and membership-card schema foundations should be reused unless subsequent endpoint/schema inspection demonstrates a concrete missing field or constraint.

## 6. Authorization and privacy contract checklist

Before implementation begins, record the exact server policy and test for each action:

- [ ] Membership application: authenticated owner can create/read/respond to own application; reviewer can make a separate review decision.
- [ ] Payment evidence: owner can submit/view own evidence; finance/reviewer can inspect only within authorized scope; upload does not approve, verify or activate.
- [ ] Payment verification: finance/reviewer action remains independent from application approval and activation.
- [ ] Payment methods: only authorized finance/admin roles can manage bank/account configuration; members see enabled payment instructions only.
- [ ] Account details: platform roles, organization links, membership status and profile attributes follow field-level access policy.
- [ ] User recovery/security actions: privileged, confirmed, reasoned, audited, expiring and secret-safe.
- [ ] Member cards: eligible member self-view and scoped admin view; no private evidence/recovery details; bulk print logs actor and selected scope.
- [ ] Selective exports: server-enforced row and field allowlists; no UI-only restriction; private address/contact/gender/education export only for a justified, authorized purpose.
- [ ] Job interest: server-enforced eligible-members-only gate on page and every endpoint; owner-only private records; no continuation token in normal display/logs; explicit employer-sharing consent.
- [ ] Screen tour and navigation: role-aware visibility, but no reliance on client navigation to enforce access.

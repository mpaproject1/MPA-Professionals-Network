# Workstream 10 — Member job-interest access and readable tracking

## Access policy
The no-vacancy job-interest workflow is for authenticated users whose account is active and who have at least one membership record with:
- `status = 'active'`
- `start_date <= current_date`
- `end_date IS NULL OR end_date >= current_date`

A role named `member` is not proof of current membership. The server enforces this policy for creation, listing, detail lookup, consent changes, sharing-history access and verified-organization search. The page also checks the account's authoritative `has_active_membership` result and directs ineligible users to `/membership`; the page check is not the security boundary.

## References and secrets
- Job-interest support reference: `MPA-JI-YYYYMMDD-NNNNNN`.
- The date and sequence are generated by the server. The existing database sequence plus the unique `public_reference` constraint and bounded retry prevent collisions.
- The continuation secret is independently generated with 256 bits of cryptographic randomness. Only its SHA-256 hash is persisted. It is not returned to the member UI, placed in the URL, or written to ordinary application logs.
- The member-facing reference is not an authenticator. Every detail and mutation query also constrains `app_user_id` to the authenticated account.

## Idempotency and audit
- Member submissions use a client-generated idempotency key, hashed before storage in `submission_idempotency_hash`; the payload fingerprint prevents reusing a key for different data.
- Support Desk status decisions for no-vacancy job-interest requests require an idempotency key. Its hash and payload fingerprint are stored per request and actor; a replay returns the recorded result without creating a second status audit event.
- Submission, status decisions and consent changes continue to write audit events. The private continuation secret and its hash are not audit metadata.

## Privacy and consent
- Job-interest records are private to the owning member and authorized MPA Support Desk workflows.
- Employer sharing remains off by default. Explicit consent is limited to selected fields and one named verified organization; Support Desk review remains required before sharing.
- Consent changes revoke prior active shares when the audience or field selection changes, preserving the existing consent boundary and share history.

## API surface
- `GET /api/v1/me/job-interests`
- `POST /api/v1/me/job-interests`
- `GET /api/v1/me/job-interests/:reference`
- `GET /api/v1/me/job-interests/:reference/sharing-history`
- `POST /api/v1/me/job-interests/:reference/sharing-consent`
- `GET /api/v1/me/job-interest-sharing-organizations?q=...`

All routes require session authentication; the service repeats membership and ownership checks. Legacy public token routes reject job-interest records. Public mentorship intake remains separate.
